Quick Start

EH UI Automation, from zero to a stabilized feature

This framework regression-tests Cytel East Horizon's design & simulation screens. Everything that makes a test "a test" — the data, the steps, the tolerances — lives in CSV files, not code. This page is the fast path: set up, add a feature, run it, read what breaks, and know which AI assistant prompt to reach for. Every deeper topic links out to the full doc that owns it.

Engine: TypeScript + Playwright Config: CSV, zero code per feature Apps: ProductDesign · ProductDecide Registry: master.csv

1What is this?

The one-paragraph mental model — read this before anything else.

A feature is one East Horizon test design (e.g. "Simon's Two-Stage", "Mean of Paired Ratios"). For each feature, the framework drives the real app in a real browser, fills it from your test data, captures the computed results, and compares them against a committed baseline with per-column tolerances. The first run of a new data combination can't fail — it just records the baseline (BASELINE_CREATED). Every run after that is a real regression check.

A feature can have a design flow (always) and an optional chained simulation flow (Simulation=YES in master.csv) that runs in the same browser session right after a green design.

The promise: adding a feature should take zero changes to core/. If you ever find yourself editing the engine to onboard one feature, the abstraction is wrong — fix the engine, not the feature, and get that past npm run validate for every other feature first.

2First-time setup

Five commands, once per machine.

terminal
# 1. install dependencies
npm install

# 2. install the Chromium browser Playwright drives (Edge/msedge uses your OS install)
npx playwright install --with-deps chromium

# 3. your own environment file — never commit this
cp .env.example .env
# then edit BASE_URL / APP_USERNAME / APP_PASSWORD inside .env

# 4. prove the setup works — no browser opens, just schema checks
npm run validate

# 5. smoke-test a known-good feature to confirm the browser side works too
npm run test -- --tags smoke

.env and .auth/ are git-ignored on purpose — never commit real credentials, and never paste them into a recording either (the repo has a pre-commit guard, but don't rely on it).

3How a feature is shaped

Every feature is the same ten folders, numbered in the order you'll touch them.

<Module>/feature_<Name>/
00_config/feature.config.json    # simulation polling, result-grid column map
01_testdata/*.csv                # project / inputset / design / simulation values — YOU author these first
02_selectors_repo/selectors.csv  # logical object name -> real locator (role/css/label/testid)
03_metadata/metadata.csv         # the ordered steps (and sim_metadata.csv for the sim flow)
04_generated_pom/                # AUTO-GENERATED Page Objects — never hand-edit
05_generated_scripts/            # AUTO-GENERATED Playwright spec — never hand-edit
06_baseline/compare.config.csv   # per-column tolerances — the most important file
06_baseline/<env>/baseline_*.csv # COMMITTED baselines + .meta.json sidecar
07_actual_results/               # this run's extracted numbers (git-ignored)
08_diffs/                        # cell-level diff.csv/.json per iteration (git-ignored)
09_html_report/                  # per-feature HTML report (git-ignored)

master.csv at the repo root is the registry — one row per TC_ID, naming the Module, Feature, Browser (chromium/msedge), whether Execute runs it in the full suite, the Environment, and whether Simulation chains on.

The one column that trips everyone up: Run inside project.csv/simulation.csv is a global veto across every testdata file that carries it, not a per-file switch. Setting Run=FALSE in simulation.csv alone will silently drop that entire iteration — design included. Flip it in lockstep across every file.

4Add a new feature

The real day-to-day loop (not the from-scratch-scaffold path — that one's in README.md if you ever need it). A small model — or a careful human — can run this verbatim.

  1. Record it. Walk the real flow once in Playwright codegen (npm run codegen -- --env test) and save the recording as recording.ts (design) and/or sim_recording.txt (simulation) under the feature's 02_selectors_repo/.
  2. Author 01_testdata/ first. Write project.csv, inputset.csv, design.csv (and simulation.csv if there's a sim flow) with real values, keyed by TC_ID + IterationID. The importer conforms to your columns — it never invents them.
  3. Run the importer — see the import-codegen card below. It writes selectors.csv, metadata.csv, and a config skeleton, binding each recorded field to your column by DOM id or on-screen label.
  4. Resolve every UNWIRED line. A field the importer couldn't match prints as ! design.csv <- wire id="sampleSize" or label="Sample Size" (recorded value: 100). Add that column (named after the id or label) or rename an existing one, then re-run — never with --seed once real data exists.
  5. Add one row to master.csv.
  6. npm run validate — schema-checks every CSV, no browser. Fix line-numbered errors and coverage warnings before you run anything.
  7. Run it (npm run test -- --testcase TC_XX). The first pass writes the baseline (BASELINE_CREATED — green, but nothing was verified yet). Screenshot-verify every iteration under artifacts/<runId>/<TC>_<ITER>/ — green isn't the same as correct.
  8. Stabilize. Fix what fails, re-run, repeat — see the error list below. Re-run the whole feature at least twice clean before calling it done.
  9. Commit — scoped to that feature's folder + its master.csv row only.
Start from a sibling, not a blank page. Pick the closest existing feature in the same family and reuse its column names/selectors so id/label wiring matches on the first pass — means → feature_DOM(PD); survival → feature_GADAR(PD); proportions → feature_RONBR(PD); one-arm → feature_SinglePoissonRate; multi-scenario → feature_BOIN. Full family map in AI_IMPORT_AGENT.md.

5Commands you'll actually use

Grouped by what you're doing. The ones scoped to one feature are tagged — swap in your own <Module>, feature_<Name> and TC_XX.

Import & wire a feature

Import the design flow

one feature
Reads recording.ts/.txt from 02_selectors_repo/, writes selectors.csv + metadata.csv, binds tokens to your existing 01_testdata columns. Creates the feature folder if it doesn't exist yet.
design import
npm run import-codegen -- <Module> feature_<Name> --tc TC_XX
real example
npm run import-codegen -- ProductDesign feature_MeanofPairedRatios --tc TC_05

Import the simulation flow

one feature
Same importer, --sim flag. Reads sim_recording.txt, writes sim_metadata.csv, binds tokens to simulation.csv. No login/navigate steps — the sim flow starts mid-app, right at the "Simulate" click, and chains after a green design run in the same browser. Selectors and compare.config.csv are shared with the design flow.
simulation import
npm run import-codegen -- <Module> feature_<Name> --tc TC_XX --sim
real example
npm run import-codegen -- ProductDesign feature_MeanofPairedRatios --tc TC_05 --sim

Don't forget to set Simulation=YES for that TC_ID in master.csv — otherwise the sim flow is wired but never runs.

Validate & run

Validate one test case

one feature
Schema-checks that feature's CSVs only — unknown actions, missing locators, dangling ${data...} references, and the "column has a value but no step reads it" coverage warning. Opens no browser; run this constantly while wiring.
validate (scoped)
npm run validate -- --testcase TC_XX
real example
npm run validate -- --testcase TC_05
# --feature feature_MeanofPairedRatios works the same way
# no flags at all = validate every feature in master.csv

Run one test case

one feature
--testcase (alias --tc) is the only flag that runs a row even when its Execute column is FALSE — handy for a feature you're still stabilizing.
run (scoped)
npm run test -- --testcase TC_XX
npm run test -- --testcase TC_XX --headed            # watch it in a visible browser
npm run test -- --testcase TC_XX --update-baseline   # approve current actuals as the new baseline
real example
npm run test -- --testcase TC_05

Share a report

Package one run as a single file

any recent run
Re-renders reports/<runId>/results.json into one self-contained HTML file you can email or Slack — the normal reports link out to artifacts/ for screenshots and break the moment you move them.
share a run
npm run report:share -- <runId>
real example
npm run report:share -- 20261028T153445_2d1097
# -> reports/20261028T153445_2d1097/run_20261028T153445_2d1097_shareable.html

Same, without screenshots

any recent run
--lite drops the embedded screenshots — ~40 KB instead of several MB, still every step with its description and baseline comparison. Good for email, bad for "what did the UI actually look like" questions.
share, lite
npm run report:share -- <runId> --lite
other useful forms
npm run report:share                 # no args = newest run, screenshots embedded
npm run report:share -- --list        # show which run IDs are available to share

Housekeeping

Scaffold a brand-new folder by hand

When you don't have a recording yet and want the empty CSV skeleton first.

scaffold
npm run scaffold-feature -- ProductDesign "YourFeature"

Clean up crashed-run leftovers

Deletes app-side projects a killed/crashed run never cleaned up.

cleanup
npm run cleanup:orphans

Generate POM/spec only

Regenerate 04_generated_pom/05_generated_scripts without running anything — useful after a selector edit.

generate
npm run generate -- --testcase TC_XX

Typecheck / unit tests

Run before committing any change under core/ or custom/.

checks
npm run typecheck
npm run unit
Selection precedence, highest wins: --testcase › --tags (+ Execute) › Execute column › --all. There is no --iteration flag — scope to one iteration by toggling Run=FALSE on the others in project.csv and simulation.csv, then restoring it afterwards.

6Common errors, and the fix

The handful you'll hit on nearly every feature. For the exhaustive A–Z catalog (30+ more, with log excerpts) see Error_Reference_Guide.md — this is the curated top of that list.

Signalvalidate warns: "column X has a value but no step enters it"
FixEither wire a step to read ${data.<file>.X}, or the column is dead (often a leftover duplicate, or literally a field's placeholder text mistaken for a real column) — confirm with a screenshot before deleting it, never guess.
A clean validate proves columns exist and parse — it does NOT prove every cell is actually read and filled.
Signalfill/select fails "field not found" immediately after a dependent dropdown's own select step
FixCheck the StepID order, not row order. The select that picks the family/branch must have a lower StepID than every field it unlocks — move it earlier, no data change needed. The field sometimes genuinely doesn't exist in the DOM until the prior selection commits.
SignalA token like ${data.design.Select Test} stops resolving after someone restructured 01_testdata
FixThe column was probably a duplicate of one that already exists elsewhere (classic pair: a stray Select Test column in design.csv duplicating inputset.csv's SelectTest). Repoint the token to the surviving column instead of re-adding the deleted one.
SignalcompareWithBaseline FAILs with a VALUE_MISMATCH right after you fixed something
FixDon't assume your fix is wrong. Open 08_diffs/diff_<TC>_<ITER>.csv, screenshot-verify the live result against testdata — if it now matches, the OLD baseline was stale. Delete 06_baseline/<env>/baseline_<TC>_<ITER>.csv + its .meta.json (or re-run with --update-baseline) and regenerate — with the user's go-ahead, it discards the previous regression reference.
SignalA checkbox-driven field only works for the check direction, never uncheck (or vice versa)
FixWhen testdata uses the literal strings check/uncheck, wire it as two steps — a check action gated SkipIf …!=check and an uncheck action gated SkipIf …!=uncheck. The action itself doesn't read the cell as a direction.
SignalOpening the simulation result by name also matches the design result ("resolved to 2 elements")
FixGive the sim result a distinct name — fill the result-name field again after Save & Simulate from its own Sim Result Name column, and open by that exact name. Also check the importer didn't collapse this second fill into the first one (same id, different recorded value) — a common superset-recording artifact.
SignalOne iteration fails at a step that has nothing to do with anything you changed, right after a DIFFERENT iteration failed in the same run
FixRe-run just that pair in isolation (Run=FALSE on everything else) before debugging the later iteration's own steps — a crashed iteration can leave the shared browser session in a state that breaks the next iteration's fresh start. Plain environment flakiness (a stuck login spinner, a slow modal) shows the same way and usually clears on an isolated retry with zero code changes.
Signalvalidate: "StepID must be an integer" after inserting a row between two existing steps
FixDecimals are only valid in Seq (cosmetic ordering, e.g. 53.1) — StepID is what the engine actually sorts and executes by, and it must be a plain integer. Renumber the block instead.
SignalA Details/secondary tab exists on the design result but times out on the simulation result (or vice versa)
FixThe two result pages aren't guaranteed to have the same tabs. A simple fixed design with no boundary/interim table often has NO sim-side Details tab at all — confirm with a live screenshot, then either delete the sim-side check (whole-feature case) or gate it with SkipIf on whatever testdata column decides it (per-iteration case).
Blank vs N/A: always write the literal string N/A in a not-applicable cell, never leave it truly blank. The comparator, SkipIf gates, and the coverage validator all key off that literal string — a blank cell doesn't reliably mean the same thing to every part of the engine.

7Prompts for GitHub Copilot

This repo ships .github/copilot-instructions.md — Copilot reads it automatically for any task here, so you don't need to re-explain the framework every time.

Two ways to invoke the import playbook

① Slash prompt

Type /import-feature in Copilot Chat, then name the feature. One-off, doesn't change your chat mode.

② Custom agent

Open the Chat mode dropdown → "Import Feature". Stays in that persona (the AI_IMPORT_AGENT.md non-negotiables) for the whole session — better when you're stabilizing one feature across many turns.

Prompts that work well

Fresh import Import ProductDesign feature_<Name> as TC_XX from the recording I just saved in 02_selectors_repo/. I've already written 01_testdata. Resolve every UNWIRED field — ask me before adding or renaming any testdata column.
Reviewing someone else's wiring feature_<Name> was wired by [you / another session] but never stabilized. Audit it against IMPORT_LESSONS.md and AI_IMPORT_AGENT.md, run npm run validate, then run TC_XX and fix whatever fails. Screenshot-verify, don't just chase green.
After a testdata restructure I've updated 01_testdata for TC_XX — column names changed. Review the wiring against the new columns, fix every broken ${data.*} token, and tell me before you touch any testdata value yourself.
Adding the Details-tab check Add the Details-tab load-only check (click → wait for the spinner to hide → assert the chart is visible) to both the design and simulation flows for feature_<Name>, the same pattern as feature_SingleProportion / feature_MeanofPairedDiff. Don't assume the sim side has the tab — confirm live.
A stale-looking baseline failure TC_XX/ITER_03 just failed compareWithBaseline. Check IMPORT_LESSONS.md's stale-baseline pattern first — screenshot-verify the live result against testdata before deciding whether this is a regression or just a stale baseline.
Why these work: each one names the exact doc/pattern to apply and sets the scope boundary (one feature, ask before touching testdata) up front — Copilot's own instructions already enforce most of this, but repeating it in-prompt keeps a long session on rails.

8Prompts for a custom agent (Claude Code)

Claude Code has the same playbook wired up as an invokable skill — .claude/skills/import-feature/. It follows AI_IMPORT_AGENT.md exactly, the same source of truth Copilot uses.

invoke the skill directly
/import-feature ProductDesign feature_<Name> TC_XX

Plain-language prompts work just as well — and are what this team actually types day to day:

Kick off a fresh import Import and wire ProductDesign feature_<Name> as TC_XX. I've recorded 02_selectors_repo/recording.ts and written 01_testdata already.
Hand back updated test data I have updated the data for TC_XX. Review and analyse, make changes accordingly and let me know if any issues.
A broad "make it work" ask Check, validate, fix wiring and run TC_XX.
Closing out the last few coverage warnings Handle the remaining warnings as well, only then start execution.
Pre-approving a known, repeatable action You may also need to regenerate the baseline files for a few iterations — I approve, you can regenerate those baseline files.
Switching browsers for a stabilized feature Switch TC_XX to Edge in master.csv and re-run it to confirm it's still green.
Keeping the shared docs current Update the docs so the lessons from this session are captured for next time (and for Copilot) — IMPORT_LESSONS.md and AI_IMPORT_AGENT.md, not just the local handoff notes.
Ambiguity gets surfaced, not guessed. If testdata looks wrong, incomplete, or ambiguous, expect the agent to stop and list the exact file/iteration/field rather than silently picking a value — that's the standing rule in both AI_IMPORT_AGENT.md and copilot-instructions.md, and the fastest way to answer is a plain "use X" / "N/A that field" reply.

10Rules that save you time

The short list of things every new user eventually learns the hard way.

Never add/rename a column silently

Check whether an existing column already covers it, propose the exact name/file/values, and wait for a yes — including while resolving UNWIRED.

Follow the testdata, don't force green

A valued field that isn't found is a real FAIL. Fix the data or the selector — never delete a step just to pass.

Every value-entering step needs a token

A blank InputValue on a fill/ select/check fires every iteration and silently overrides earlier data-driven choices.

Green ≠ correct

Screenshot-verify every iteration under artifacts/, especially the first run of any new data combination.

Scope stays inside one feature

Edit only that feature's folder + its master.csv row. A real framework bug gets tested on a throwaway feature first, then re-validated across everything.

Baselines are a reviewed act

Never let a run write into 06_baseline/ implicitly. --update-baseline is an explicit, confirmed decision — commit the baseline change in its own reviewed diff.
